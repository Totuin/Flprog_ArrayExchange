## 1. Назначение и архитектура

Библиотека обеспечивает двусторонний обмен элементами массивов контроллера с внешним устройством через UART. Способ хранения не регламентируется: RAM, кеш EEPROM, внешняя память или вычисляемые значения. Библиотека не владеет массивами, не задаёт их адреса в EEPROM и не требует копии всего массива в RAM.

```text
Внешнее приложение
        ↕ ASCII / CRC16
FlprogAbstractUartExecutor
        ↕
FlprogUartArrayExchange
        ↕ реестр адаптеров по ID
FlprogAbstractExchangeArray
        ├── FlprogExchangeTypedArray<bool>    → FlprogExchangeBoolArray
        ├── FlprogExchangeTypedArray<int16_t> → FlprogExchangeInt16Array
        └── FlprogExchangeTypedArray<String>  → FlprogExchangeStringArray
        ↕ функции read / write
Массивы проекта (RAM, кеш EEPROM и т. д.)
```

`ID` — постоянный идентификатор массива в пределах одного исполнителя. `slot` — его порядковый номер в переданном реестре. Оба имеют тип `uint16_t`, но не взаимозаменяемы. ID 0 допустим; уникальность обязательна. Индексация элементов и слотов начинается с нуля. Нулевой размер массива разрешён реализацией, но ни один индекс такого массива не допустим.

Объекты адаптеров, исполнитель UART, реестр указателей и строки имён должны существовать всё время обмена. Библиотека их не освобождает. Настройку и обмен выполнять из основного потока/цикла, не из ISR. Не изменять реестр или колбэки во время транзакции.

## 2. Подключение и пример

Заголовок: `#include <flprogArrayExchange.h>`. Зависимости: Arduino (`String`, `millis()`), интерфейс `FlprogAbstractUartExecutor` из `Flprog_Utilites` (`flprogUartBase.h`) и реализация UART, принятая в проекте. Для стандартного `FlprogUartExecutor` подключается `flprogUart.h`; обычные зависимости RT_HW должны быть установлены.

Пример для Arduino/FLProg (RAM, три независимых адаптера, UART 1, 115200 8N1). Для обычного C++ функции доступа предварительно объявлены явными прототипами. Номер UART поменять согласно целевой плате.

```cpp
#include <flprogUtilites.h>
#include <flprogUart.h>
#include <flprogArrayExchange.h>

constexpr uint8_t UART_NUMBER = 1;
constexpr uint16_t N = 3;
String names[N] = {"Первый", "Второй", "Третий"};
int16_t numbers[N] = {10, 20, 30};
bool flags[N] = {true, false, true};

String readName(uint16_t i) { return names[i]; }
void writeName(String v, uint16_t i) { names[i] = v; }
int16_t readNumber(uint16_t i) { return numbers[i]; }
void writeNumber(int16_t v, uint16_t i) { numbers[i] = v; }
bool readFlag(uint16_t i) { return flags[i]; }
void writeFlag(bool v, uint16_t i) { flags[i] = v; }

FlprogUartExecutor uart;
FlprogExchangeStringArray aNames(1, N);
FlprogExchangeInt16Array aNumbers(2, N);
FlprogExchangeBoolArray aFlags(3, N);
FlprogAbstractExchangeArray* arrays[] = {
    &aNames, &aNumbers, &aFlags
};
FlprogUartArrayExchange exchange;

void setup() {
    uart.setSpeedUart(115200, UART_NUMBER);
    uart.setDataBitUart(8, UART_NUMBER);
    uart.setParityUart(0, UART_NUMBER);
    uart.setStopBitUart(1, UART_NUMBER);
    uart.beginUart(UART_NUMBER);

    aNames.setReadFunction(readName);
    aNames.setWriteFunction(writeName);
    aNames.setName("Названия");
    aNames.setMaxLength(20);

    aNumbers.setReadFunction(readNumber);
    aNumbers.setWriteFunction(writeNumber);
    aNumbers.setName("Числа");
    aNumbers.setLimits(-1000, 1000);

    aFlags.setReadFunction(readFlag);
    aFlags.setWriteFunction(writeFlag);
    aFlags.setName("Флаги");

    exchange.setUart(&uart, UART_NUMBER);
    bool ok = exchange.setArrays(arrays, sizeof(arrays)/sizeof(arrays[0]));
    exchange.setWriteEnable(ok); // Только для демонстрации на стенде.
}
void loop() {
    exchange.pool();
}
```

В FLProg вместо RAM-функций подставляются сгенерированные `readFlprogArray_...` и `writeFlprogArray_...`. В глобальной области достаточно конструктора с двумя аргументами, колбэки назначаются в `setup()` после объявления прототипов (Arduino обычно создаёт их автоматически). Для автоматики разрешение записи вычислять перед `pool()` из текущего безопасного состояния и признака корректной конфигурации. При использовании EEPROM отдельно вызывать её штатный `pool()`.

## 3. API адаптеров массивов

### 3.1. FlprogAbstractExchangeArray

Абстрактный базовый класс, предназначенный для хранения разных адаптеров в едином массиве указателей. Самостоятельно не инстанцируется.

| Метод | Назначение / контракт |
|---|---|
| `FlprogAbstractExchangeArray(uint16_t id, uint16_t size)` | Задаёт идентификатор и число элементов. Не выделяет память массива. |
| `virtual ~FlprogAbstractExchangeArray()` | Виртуальный деструктор. |
| `uint16_t getId() const` | ID массива. |
| `uint16_t getSize() const` | Число элементов. |
| `const char* getName() const` | Указатель на имя (по умолчанию пустая строка). |
| `void setName(const char* name)` | Сохраняет указатель, не копирует. `nullptr` превращается в пустую строку. Имя: корректный UTF-8 до 32 байт, без NUL внутри. Проверка выполняется при DESCRIBE, не в setter. |
| `void setWriteEnable(bool enable)` | Локальный запрет/разрешение записи адаптера. По умолчанию true. Не открывает глобальную запись и сам не сбрасывает транзакцию. |
| `virtual uint8_t getType() const = 0` | Код типа протокола. |
| `virtual uint16_t getMaxLength() const` | Максимум байт строкового элемента, по умолчанию 0 (для чисел). |
| `virtual bool canRead() const = 0` | Доступность чтения адаптера. |
| `virtual bool canWrite() const = 0` | Доступность записи адаптера, без учёта глобального флага исполнителя. |
| `virtual bool encode(uint16_t index, char* out, size_t capacity) const = 0` | Получает элемент и кодирует его в ASCII-представление протокола с завершающим NUL; capacity включает NUL. false при ошибке. |
| `virtual bool validate(const char* text) const = 0` | Проверяет ASCII-представление значения; не меняет массив. Индекс, доступ и состояние транзакции проверяются исполнителем отдельно. |
| `virtual bool apply(uint16_t index, const char* text) = 0` | Преобразует и применяет значение. false означает ошибку, но запись уже могла произойти. |
| `bool writeEnabled() const` (protected) | Возвращает локальный флаг записи. |

`encode`, `validate`, `apply` — виртуальный интерфейс для реализации новых типов, а не замена обычным функциям доступа. При прямом вызове глобальный write gate и CRC не проверяются. Передавать корректные указатели на буферы; для `encode` предоставлять достаточную ёмкость. Стабильный ABI расширений не гарантирован.

### 3.2. FlprogExchangeTypedArray<T>

Шаблонный абстрактный класс: добавляет типизированные функции доступа, используется всеми тремя реальными классами.

```cpp
using ReadFunction  = T (*)(uint16_t index);
using WriteFunction = void (*)(T value, uint16_t index);
```

| Метод | Назначение |
|---|---|
| `FlprogExchangeTypedArray(uint16_t id, uint16_t size, ReadFunction read = nullptr, WriteFunction write = nullptr)` | Устанавливает размер, ID и необязательные функции доступа. Конструктор наследуется конкретными типами. |
| `void setReadFunction(ReadFunction read)` | Назначает чтение; `nullptr` отключает чтение. |
| `void setWriteFunction(WriteFunction write)` | Назначает запись; `nullptr` отключает запись. |
| `bool canRead() const` | true, если функция чтения назначена. |
| `bool canWrite() const` | true, если назначена функция записи и локальный флаг записи включён. |

Защищённые члены `_read`, `_write` доступны производным классам. Колбэки — обычные указатели на функции: нестатический метод объекта и захватывающая lambda непосредственно не подходят. `String` передаётся по значению, как и остальные типы. Порядок аргументов записи строго **значение, затем индекс**. Возврат `void` не позволяет сообщить ошибку записи напрямую: конкретные адаптеры при наличии read-функции проверяют результат повторным чтением. Без read-функции успешный вызов write считается успешным применением, но сохранение не подтверждается.

Допустимы read-only (только read), write-only (только write), read/write и недоступный адаптер (оба nullptr). Рекомендуется read/write для обратной проверки. Изменять колбэки только вне обмена.

### 3.3. FlprogExchangeBoolArray

Конструктор: `FlprogExchangeBoolArray(uint16_t id, uint16_t size[, ReadFunction read, WriteFunction write])` (оба необязательных аргумента по умолчанию nullptr). Наследует все методы typed/base.

- `getType()` → `FLPROG_EXCHANGE_TYPE_BOOL` (1).
- `encode(...)` читает bool и выдаёт `0` или `1` (буфер минимум 2 байта).
- `validate(...)` принимает только односимвольные строки `0` и `1`.
- `apply(...)` проверяет доступ, индекс и значение, вызывает `_write(bool, index)`, при наличии чтения сравнивает результат.

### 3.4. FlprogExchangeInt16Array

Конструктор с ID, размером и необязательными функциями чтения/записи `int16_t`.

| Метод | Назначение |
|---|---|
| `bool setLimits(int16_t minimum, int16_t maximum)` | Задаёт включительные границы для **всех элементов массива**. false, если minimum > maximum; прежние границы сохраняются. По умолчанию −32768…32767. |
| `uint8_t getType() const` | Тип 2. |
| `bool encode(uint16_t index, char* out, size_t capacity) const` | Формирует десятичное число, в том числе отрицательное; до 6 символов + NUL. Чтение не ограничивается setLimits. |
| `bool validate(const char* text) const` | Проверяет синтаксис int16_t, отсутствие переполнения, попадание в заданные границы. |
| `bool apply(uint16_t index, const char* text)` | Проверяет индекс/доступ/диапазон, вызывает write и сравнивает readback, если доступен. |

Границы не передаются в DESCRIBE в протоколе v1. API чтения границ не предусмотрен. Для разнородного массива настроек не устанавливать один диапазон, если он не подходит всем элементам; специфические проверки — ответственность приложения контроллера. Отбрасывание записи внутри void-колбэка может дать APPLY_PARTIAL, поэтому не заменяет полноценную предварительную проверку набора.

### 3.5. FlprogExchangeStringArray

Конструктор с ID, размером и необязательными функциями `String`.

| Метод | Назначение |
|---|---|
| `void setMaxLength(uint16_t bytes)` | Максимум байт UTF-8 в одном элементе. По умолчанию 64, значения выше 64 ограничиваются до 64. 0 разрешает только пустую строку. |
| `uint16_t getMaxLength() const` | Текущий лимит. |
| `uint8_t getType() const` | Тип 3. |
| `bool encode(uint16_t index, char* out, size_t capacity) const` | Читает `String`, проверяет длину и UTF-8, кодирует в HEX (до 128 символов + NUL). |
| `bool validate(const char* text) const` | Проверяет чётную длину HEX, символы, декодированный UTF-8, отсутствие NUL и лимит размера. |
| `bool apply(uint16_t index, const char* text)` | Декодирует HEX, формирует `String` (возможно выделение памяти), вызывает write и при наличии read сравнивает байты. |

Лимит задаётся **в байтах, а не в символах**. Например, `Тест` содержит 4 буквы и 8 байт UTF-8. При лимите 20 обычно помещается 10 кириллических букв. Реальная ёмкость элемента в EEPROM должна быть не меньше требуемой (учесть формат хранения и терминатор, если он нужен конкретному хранилищу).

## 4. API FlprogUartArrayExchange

Исполнитель создаётся без аргументов: `FlprogUartArrayExchange exchange;`. В начале UART не назначен, реестр пуст, запись запрещена.

| Метод | Контракт |
|---|---|
| `void setUart(FlprogAbstractUartExecutor* uart, uint8_t number)` | Назначает исполнитель и номер UART. Сбрасывает транзакцию и внутренние RX/TX/состояние отбрасывания строки. Не очищает аппаратный UART и не задаёт его скорость. `nullptr` или порт 255 отключают обработку. |
| `bool setArrays(FlprogAbstractExchangeArray* const* arrays, uint16_t count)` | Регистрирует массив указателей. false при nullptr с ненулевым count, нулевом указателе внутри либо повторном ID. При ошибке реестр остаётся пустым; прежний уже сброшен. Пустой реестр допустим. В любом случае сбрасывает транзакцию, не копирует реестр. |
| `void setWriteEnable(bool enable)` | Глобальное разрешение записи. false немедленно сбрасывает отложенные записи, не откатывая уже применённые. Чтение остаётся доступно. true не восстанавливает отменённую транзакцию. |
| `bool isTransactionActive() const` | true между успешным BEGIN и закрытием транзакции. Тайм-аут обрабатывается только в pool(). Не является признаком завершения EEPROM. |
| `void setTimeout(uint32_t ms)` | Тайм-аут отсутствия активности транзакции, по умолчанию 10000 мс; 0 заменяется на 1 мс. |
| `void setRxBudget(uint16_t bytes)` | Лимит байт приёма за вызов pool(), по умолчанию 32; 0 заменяется на 1. |
| `void setTxBudget(uint16_t bytes)` | Лимит байт отправки за вызов pool(), по умолчанию 16; 0 заменяется на 1. |
| `void pool()` | Опрос UART, обработка тайм-аута, накопление строки, выполнение одной команды или передача части ответа. Вызывать регулярно в loop(). |
| `static uint16_t crc16(const char* data, size_t length)` | CRC-16/CCITT-FALSE над заданным количеством байт; NUL не включается, если не входит в length. |

Используются `availableUart(uint8_t number)`, `readUart(uint8_t number)` и `writeUart(uint8_t value, uint8_t number)`. При непросланном ответе исполнитель сначала обслуживает TX и не разбирает следующую команду в тот же вызов. После приёма полной команды формирование ответа происходит в текущем pool(), физическая выдача ответа — в последующих вызовах. Наращивание бюджетов повышает потенциальную пропускную способность и длительность одного вызова. Это не гарантия строго неблокирующей аппаратной передачи.

## 5. Константы и память

| Макрос | Значение | Смысл |
|---|---:|---|
| `FLPROG_EXCHANGE_TYPE_BOOL` | 1 | bool |
| `FLPROG_EXCHANGE_TYPE_INT16` | 2 | int16_t |
| `FLPROG_EXCHANGE_TYPE_STRING` | 3 | String |
| `FLPROG_EXCHANGE_READ` | 1 | Бит чтения |
| `FLPROG_EXCHANGE_WRITE` | 2 | Бит записи |
| `FLPROG_EXCHANGE_MAX_STRING_BYTES` | 64 | Глобальная длина строк в байтах UTF-8 |
| `FLPROG_EXCHANGE_MAX_NAME_BYTES` | 32 | Максимальная длина имени в байтах UTF-8 |
| `FLPROG_EXCHANGE_MAX_TRANSACTION_ITEMS` | 64 | Максимум разных элементов за транзакцию |
| `FLPROG_EXCHANGE_LINE_SIZE` | 192 | Размер каждого RX/TX-буфера |
| `FLPROG_EXCHANGE_PROTOCOL_VERSION` | 1 | Версия формата протокола |
| `FLPROG_EXCHANGE_TRANSACTION_BUFFER_SIZE` | 1024 (по умолчанию) | Внутренний staging-буфер, допустимо 7…65535 байт |

Только размер staging-буфера предусмотрен как переопределяемый флаг сборки. Например, `-DFLPROG_EXCHANGE_TRANSACTION_BUFFER_SIZE=64` должен действовать **во всех единицах трансляции**, включая библиотеку, а не только в скетче. Иначе различаются размеры класса. Остальные константы — значения текущей реализации.

Объект содержит staging-буфер и два буфера по 192 байта: при 1024 это 1408 байт непосредственно на массивы буферов, при 64 — 448. Дополнительно нужны служебные поля, сами адаптеры, стек и память строк. Staging не выделяется через malloc/new; `String` может динамически выделять память. Точный общий размер проверять на целевом Core (`sizeof`, отчёт сборки).

Запись во внутреннем буфере: `id` (2 байта LE), `index` (2), длина значения вместе с NUL (2), ASCII-значение с NUL. Цена элемента — **7 + длина ASCII-значения**. Это внутренний формат хранения, не формат UART.

| Значение | Размер ASCII | Staging |
|---|---:|---:|
| bool `1` | 1 | 8 |
| int16 `-32768` | 6 | 13 |
| Пустая строка | 0 | 7 |
| `Тест` (8 байт UTF-8) | 16 | 23 |
| Строка 20 байт | 40 | 47 |
| Строка 64 байта | 128 | 135 |

При 64 байтах staging максимальная одиночная строка — 28 байт UTF-8 (7 + 56 = 63), даже если её адаптер объявил 64; 29 уже не помещается. При 1024 байтах 21 строка по 20 байт помещается в одну транзакцию. Дополнительно всегда действует ограничение числа элементов. Клиент обязан учитывать оба лимита из INFO, а не размер массива. Увеличение массива с 50 до 100 не требует увеличения staging, если клиент умеет делить записи на порции.

## 6. Формат протокола, типы и CRC

### 6.1. Кадр

```text
COMMAND;arg1;arg2*HHHH\n
OK;response;arg1*HHHH\n
ERROR;code*HHHH\n
```

Здесь `\n` обозначает один физический байт LF (0x0A), не два печатных символа. Допускается завершающий CRLF. Входные данные — печатный ASCII 0x20…0x7E; CR перед LF удаляется. Пустые строки игнорируются. Пробелы не удаляются, регистр команд значим. Разделитель полей `;`; последнее пустое поле сохраняется. Настраивать UART отдельно; скорость и параметры кадра не являются частью протокола (115200 8N1 — используемый пример).

Максимум 191 байт входной строки до LF, включая CRC и возможный CR. Более длинная строка либо недопустимый управляющий/не-ASCII байт приводит к отбрасыванию до ближайшего LF и ответу ERROR;LINE. Исходящий кадр помещается в буфер 192 байта; тело ответа не длиннее 185 байт, плюс `*`, 4 цифры и LF. При переполнении формируется ERROR;RESPONSE_TOO_LONG. Отправка запросов последовательно: один запрос — один полный ответ, без конвейеризации. Нет спонтанных уведомлений, идентификатора сообщения или номера сессии.

### 6.2. CRC

CRC-16/CCITT-FALSE (также CRC-16/IBM-3740): ширина 16, poly 0x1021, init 0xFFFF, refin=false, refout=false, xorout=0x0000. Контрольный вектор ASCII `123456789` → `29B1`. CRC вычисляется по всем байтам тела перед последней `*`, включая разделители и пустое поле, но без `*`, CRC, CR, LF и завершающего NUL. Передаётся четырьмя HEX-цифрами; вход принимает оба регистра, выход — верхний. Некорректный суффикс отклоняется, даже если CRC для команды необязателен.

| Команды | CRC запроса |
|---|---|
| PING, INFO, DESCRIBE, GET | Необязателен (для ручной отладки); для программного клиента рекомендуется всегда |
| BEGIN, SET, COMMIT, CANCEL | Обязателен |
| Все ответы, включая ERROR | Обязателен |

Пример формирования кадра в Python:

```python
from binascii import crc_hqx

def frame(body: str) -> bytes:
    payload = body.encode('ascii')
    return payload + f'*{crc_hqx(payload, 0xFFFF):04X}\n'.encode('ascii')

def unframe(raw: bytes) -> str:
    if not raw.endswith(b'\n'):
        raise ValueError('Incomplete frame')
    raw = raw[:-1]
    if raw.endswith(b'\r'):
        raw = raw[:-1]
    payload, star, checksum = raw.rpartition(b'*')
    if not star or len(checksum) != 4 or any(c not in b'0123456789ABCDEFabcdef' for c in checksum):
        raise ValueError('Invalid CRC field')
    if crc_hqx(payload, 0xFFFF) != int(checksum, 16):
        raise ValueError('CRC mismatch')
    return payload.decode('ascii')
```

### 6.3. Поля и представления значений

- ID, slot, index, размер, число элементов: десятичные цифры без знака и пробелов, диапазон uint16_t (0…65535); ведущие нули допустимы. Команды дополнительно проверяют нужные пределы.
- Bool: только `0` или `1`.
- Int16: десятичное целое −32768…32767, знак минус необязателен; `+` не допускается. Ведущие нули и `-0` принимаются; ответы нормализуются десятичным форматированием.
- String и name: HEX байтов UTF-8, два HEX-символа на один байт, без пробелов. На входе допустим любой регистр HEX; выход uppercase. Пустая строка — пустое поле. Встроенный NUL, невалидный UTF-8, суррогаты, overlong, кодовые точки выше U+10FFFF запрещены. HEX позволяет передавать `;`, `*` и другие символы без конфликта с кадрированием.

```python
value = 'Тест'.encode('utf-8').hex().upper()  # D0A2D0B5D181D182
text = bytes.fromhex(value).decode('utf-8')
```

| type | Тип | Значение в протоколе |
|---:|---|---|
| 1 | bool | `0`, `1` |
| 2 | int16_t | `0`, `120`, `-42` |
| 3 | String | `D0A2D0B5D181D182`, пустое поле |

При появлении неизвестного типа клиент не должен трактовать его как известный. Типы uint16_t, int32_t, float и другие в версии 0.1.2 не реализованы.

## 7. Команды и ответы

Ниже приведены тела кадров **без CRC и LF**. При отправке использовать правила раздела 6. Все ответы начинаются с OK или ERROR. Других успешных команд в версии 1 нет.

| Запрос | Успешный ответ |
|---|---|
| `PING` | `OK;PONG` |
| `INFO` | `OK;INFO;version;count;maxStringBytes;stagingBytes;maxItems;writeEnable` |
| `DESCRIBE;slot` | `OK;ARRAY;id;type;size;flags;maxLength;nameHex` |
| `GET;id;index` | `OK;VALUE;id;index;value` |
| `BEGIN;items` | `OK;BEGIN;items` |
| `SET;id;index;value` | `OK;SET;id;index` |
| `COMMIT` | `OK;APPLIED;items` |
| `CANCEL` | `OK;CANCELLED` |

### PING

Проверка связи и совместимого обработчика. Не меняет состояние транзакции. Ответ `OK;PONG`.

### INFO

Описание текущего исполнителя и его глобальных лимитов. Поля ответа:

| Поле | Значение |
|---|---|
| version | Версия протокола, 1 (не версия библиотеки) |
| count | Число зарегистрированных адаптеров |
| maxStringBytes | Глобальный максимум UTF-8 строки, 64 |
| stagingBytes | Фактический размер внутреннего буфера в байтах |
| maxItems | Верхний предел числа элементов транзакции, 64 |
| writeEnable | Глобальный флаг записи: 0/1 |

Пример `OK;INFO;1;4;64;1024;64;1`: зарегистрированы 4 адаптера, staging 1024, глобальная запись разрешена. Это не означает, что все адаптеры доступны на запись.

### DESCRIBE;slot

Описывает адаптер по порядковому номеру, 0…count−1. Для перечисления использовать INFO.count, затем DESCRIBE всех слотов. Поля:

| Поле | Смысл |
|---|---|
| id | Уникальный ID для GET/SET |
| type | Код типа |
| size | Число элементов |
| flags | Битовая маска прав |
| maxLength | Лимит UTF-8 для String; 0 для bool/int16 |
| nameHex | Имя из setName в HEX; может быть пустым |

Флаги: 0 — нет доступа; 1 — только чтение; 2 — только запись; 3 — чтение/запись. Бит записи выставляется, только если canWrite() адаптера и глобальное разрешение записи одновременно true. При изменении разрешений необходимо перечитать метаданные. ID не обязан совпадать со slot или возрастать. Например, корректен порядок ID 1, 3, 2, 4. `setLimits()` числовые границы не передаёт.

### GET;id;index

Читает текущий элемент по ID. Индекс 0…size−1. Во время активной транзакции возвращаются фактические данные массива (не staging). Операция может завершиться ошибкой READ_VALUE, например при некорректной UTF-8 строке в хранилище. Ответ с пустой строкой сохраняет завершающий `;` после index.

### BEGIN;items

Открывает единственную активную транзакцию. items — число **различных записываемых элементов**, допускаются разные массивы. Предел 1…maxItems, а также items*7 <= stagingBytes. Последняя проверка лишь необходимое условие: реальное заполнение проверяется каждым SET. Успешный BEGIN обнуляет счётчики staging, но ничего не записывает в пользовательские массивы. Второй BEGIN при активной транзакции даёт ACTIVE.

### SET;id;index;value

Проверяет ID, индекс, разрешения, тип, диапазон значения. Копирует ASCII-значение в staging, но не вызывает write. Число элементов и байты буфера ограничены. Повтор того же ID/index с **точно тем же ASCII-значением** подтверждается без увеличения счётчика и продлевает тайм-аут. Повтор того же элемента с другим текстом отклоняется (DUPLICATE), даже если декодированное значение эквивалентно. Для изменения уже подготовленного значения отменить транзакцию и начать новую.

Ответ OK;SET подтверждает предварительную запись в staging, не в пользовательский массив и не в EEPROM.

### COMMIT

Требует активной транзакции и ровно items уникальных записей. Выполняет полный предварительный проход: проверяет доступ, ID, индекс и validate каждого элемента. Затем вызывает apply последовательно в порядке принятия SET, в одном вызове pool(). При наличии read-функции каждый адаптер сравнивает записанное значение с прочитанным.

`OK;APPLIED;items` — все apply вернули true, транзакция закрыта. Это не подтверждение физического сохранения EEPROM. При ошибке проверки PRECHECK транзакция закрывается без применения. При ошибке apply возвращается `ERROR;APPLY_PARTIAL;applied;id;index` и транзакция закрывается. applied — число полностью успешных предыдущих apply; указанный неуспешный элемент также мог измениться. Отката нет.

### CANCEL

Закрывает транзакцию, сбрасывает staging. Успешен даже при отсутствии транзакции или отключённой глобальной записи. Удаляет только отложенные данные, ранее применённые не восстанавливает. Требует корректную CRC.

## 8. Транзакции, тайм-ауты и коды ошибок

```text
                  BEGIN
    IDLE ───────────────────→ ACTIVE
      ↑                        │  SET → staging
      │                        │  GET → текущий массив
      │                        │
      ├── CANCEL / timeout ────┤
      ├── writeEnable=false ───┤
      ├── PRECHECK failed ─────┤
      └── COMMIT (apply) ──────┘
```

Тайм-аут отсчитывается от успешного BEGIN или принятого SET, включая идентичный повтор. Чтение, ошибки и прочие команды его не продлевают. Проверяется при каждом pool() (если UART назначен), в том числе перед обработкой TX. При срабатывании транзакция молча сбрасывается; последующий SET или COMMIT получает NO_TRANSACTION, если запись разрешена. Сравнение millis() сделано unsigned-разностью, устойчивой к обычному переполнению счётчика. Для ручной отладки допустимо `exchange.setTimeout(60000);`. Это не тайм-аут ожидания ответа в ПК.

Все коды ошибок, присутствующие в исходниках 0.1.2:

| Код | Причина | Состояние / действие |
|---|---|---|
| `CRC` | Некорректный формат или несовпадение CRC | Состояние не меняется; исправить кадр |
| `CRC_REQUIRED` | Записывающая команда без CRC | Состояние не меняется |
| `LINE` | Слишком длинная строка или запрещённый байт | Строка отброшена; staging не сбрасывается |
| `FIELDS` | Слишком много полей (более четырёх) или неверное число полей команды записи | Исправить формат |
| `COMMAND` | Неизвестная команда либо неверное число полей запроса чтения | Исправить команду |
| `SLOT` | Недопустимый слот DESCRIBE (включая ошибку числового формата) | Перечитать INFO |
| `NAME` | Слишком длинное/некорректное имя адаптера | Исправить setName на контроллере |
| `NUMBER` | Неверный формат или диапазон ID/index | Исправить аргументы GET/SET |
| `ID` | Массив с таким ID отсутствует | Перечитать DESCRIBE |
| `INDEX` | Индекс >= size | Исправить индекс |
| `READ_DISABLED` | Не задана функция чтения | Пропустить чтение |
| `READ_VALUE` | encode вернул false | Проверить данные/лимит строки и UTF-8 |
| `WRITE_DISABLED` | Запрещена запись | При глобальном запрете транзакция сбрасывается; при запрете отдельного адаптера SET отклоняется без сброса |
| `ACTIVE` | BEGIN при уже активной транзакции | CANCEL перед новой транзакцией |
| `COUNT` | Недопустимый items в BEGIN либо избыток новых SET | Пересчитать количество; активная транзакция при SET сохраняется |
| `NO_TRANSACTION` | SET/COMMIT без активной транзакции | Начать новую после оценки состояния |
| `VALUE` | validate отклонил значение | Исправить тип/диапазон/HEX |
| `DUPLICATE` | Этот ID/index уже подготовлен с другим ASCII-значением | CANCEL и новый BEGIN |
| `BUFFER` | Недостаточно места для очередного SET | CANCEL, уменьшить порцию |
| `INCOMPLETE` | COMMIT до получения нужного числа элементов | Транзакция сохраняется; дослать элементы либо CANCEL |
| `PRECHECK` | Повторная проверка перед apply не прошла | Транзакция сброшена, ничего не применено |
| `APPLY_PARTIAL` | Ошибка apply; формат с тремя дополнительными полями | Транзакция сброшена, часть данных могла измениться; обязательная сверка и восстановление |
| `RESPONSE_TOO_LONG` | Переполнение буфера формирования ответа | Ошибка формирования; состояние могло уже измениться, для записи нужна сверка |

Если отдельно не указано и состояние не изменилось по тайм-ауту, ошибка не закрывает активную транзакцию. После транспортной ошибки безопаснее отменить непроверенную транзакцию (если COMMIT ещё не отправлен) и повторно прочитать нужные данные. CRC — проверка целостности кадра, не аутентификация.

## 9. Рекомендуемый алгоритм внешнего приложения

1. Открыть согласованный UART и обеспечить эксклюзивное владение портом. Не смешивать протокол с логами и сторонними командами.
2. PING → INFO. Проверить версию протокола, сохранить count, stagingBytes, maxItems, maxStringBytes и writeEnable.
3. Выполнить DESCRIBE для всех slot. Хранить данные по ID и типу, не предполагать фиксированный порядок. Проверять права, поддерживаемые типы и размеры.
4. Прочитать GET каждого нужного элемента с проверкой CRC, полей и диапазонов. Хранить исходные и изменённые значения отдельно. Для write-only исходное значение неизвестно.
5. Перед записью повторно запросить описание и права, проверить совместимость схемы и исходных значений. Это предотвращает часть конфликтов, но не является блокировкой на контроллере.
6. Проверить формат всех новых значений, ограничение размера строки и вычислить staging каждого изменения. Разбить список на порции по maxItems и stagingBytes; если один элемент не помещается, явно сообщить об ошибке. Не использовать size массива как число элементов транзакции без расчёта лимитов.
7. Для каждой порции: BEGIN с точным числом элементов → SET по одному с подтверждением → COMMIT → GET для обратной проверки каждого читаемого элемента. Не отправлять новую команду до получения полного проверенного ответа. Отслеживать уже подтверждённые порции.
8. При ошибке до COMMIT попробовать CANCEL; при потерянном/некорректном ответе COMMIT или APPLY_PARTIAL считать результат неопределённым/частичным. Прочитать данные заново; не повторять вслепую COMMIT. В режиме write-only невозможно подтвердить фактическое значение чтением.
9. При работе с прикладной структурой из нескольких массивов применять её правила согласованности дополнительно. В редакторе рецептов счётчик количества записывается последним, в отдельной порции, после проверки предыдущих порций. Это не делает весь набор атомарным. Запуск оборудования при несогласованном наборе должен быть запрещён.
10. При необходимости подтверждения долговременного сохранения использовать отдельный прикладной механизм; в текущем протоколе нет команд статуса физической записи или EEPROM flush.

На ПК тайм-аут ответа задаётся с учётом частоты pool(), размера ответа, скорости UART и длительности пользовательских функций. Для повторного соединения сначала завершить/отменить старую транзакцию и перечитать состояние, не предполагать, что сброс соединения автоматически отменил её на контроллере.

## 10. Проверенные примеры

### 10.1. Ручной обмен

Каждая строка отправляется с LF. В первом примере запросы чтения без CRC, в остальных CRC обязательна. Пример соответствует реальному стендовому тесту 17.11.2026: один строковый массив ID 1, 20 элементов, максимальная длина 20, имя пустое.

| Запрос | Ответ |
|---|---|
| `PING` | `OK;PONG*BD2F` |
| `INFO` | `OK;INFO;1;1;64;1024;64;1*862D` |
| `DESCRIBE;0` | `OK;ARRAY;1;3;20;3;20;*B511` |
| `GET;1;0` (до записи) | `OK;VALUE;1;0;*24F0` |
| `BEGIN;1*7736` | `OK;BEGIN;1*887B` |
| `SET;1;0;D0A2D0B5D181D182*ED5B` | `OK;SET;1;0*A6EC` |
| `COMMIT*7BB2` | `OK;APPLIED;1*23A3` |
| `GET;1;0` (после записи) | `OK;VALUE;1;0;D0A2D0B5D181D182*059B` |

После отключения и повторного включения питания значение `Тест` прочиталось обратно. Тест подтверждает интеграцию с EEPROM данного стенда, но не гарантию атомарной записи на любой платформе.

### 10.2. Утилита расчёта CRC

В исходном архиве библиотеки уже присутствует `tests/frame.py`:

```sh
python tests/frame.py "BEGIN;1"
python tests/frame.py "SET;2;0;42"
python tests/frame.py --hex "Тест"
python tests/frame.py "COMMIT"
python tests/frame.py "CANCEL"
```

Она печатает подготовленную строку, сама UART не открывает. В мониторе включить отправку LF или CRLF. Для ручного обмена учитывать стандартный тайм-аут 10 с между BEGIN и следующим успешным SET, а также между последним SET и COMMIT.

### 10.3. Тесты

`tests/run.sh` и `tests/test_exchange.cpp` — переносимые тесты C++ с имитаторами Arduino и UART. Отчёт исходной версии: `TEST_REPORT.md`. ## 11. Ограничения и правила интеграции

- Нет динамического выделения staging и RX/TX буферов; операции `String` могут выделять память. Учитывать минимальную память и stack на AVR/других ограниченных контроллерах.
- Не гарантирована строго неблокирующая UART-отправка: базовый интерфейс не сообщает свободный TX-буфер или результат writeUart. Бюджеты ограничивают число обрабатываемых байт, не абсолютную длительность pool(). COMMIT выполняет все apply в одном вызове, до 64 элементов. Измерять фактическую длительность на целевом Core.
- Нет реентерабельности, потокобезопасности и блокировок пользовательских данных. Не вызывать API из ISR; переносить чтение/изменение общих параметров в основной цикл либо организовать корректную синхронизацию.
- Транзакция является предварительной буферизацией, а не ACID. До COMMIT никакой write не вызывается этим исполнителем; после начала apply возможна частичная запись. Нет отката, журналирования с восстановлением после питания, блокировки массива для других пользователей, атомарности нескольких порций или снимка всех прочитанных массивов.
- Void-функция записи может завершиться без сохранения. Readback проверяет только видимое read-значение, часто RAM-кеш; не проверяет физическое состояние EEPROM. Нет признака EEPROM durable в API.
- Нет аутентификации, шифрования, номеров транзакций и защиты от воспроизведения кадров. CRC не является средством безопасности.
- Границы setLimits общие для массива. Нет индивидуальных лимитов, метаданных единиц измерения, межэлементной проверки, пользовательского callback предварительной валидации или схемы рецептов в протоколе v1. Прикладную логику держать отдельно.
- Для технологического оборудования (включая автоклав) необходимы независимые аппаратные защиты, надёжные допустимые пределы на контроллере, запрет записи во время процесса, признак валидности полного набора и блокировка запуска при неполном/неподтверждённом обновлении. Тайм-аут и CRC этих защит не заменяют.

### Версионность

Версия библиотеки и протокола — разные понятия. При расширении типового набора необходимо согласовать коды типов, форматы, ограничения, функции кодогенератора и внешние клиенты; не изменять смысл ранее существующих кодов без продуманной совместимости. Внешние приложения должны использовать INFO/DESCRIBE для определения фактической конфигурации, а не жёстко зашитую вместимость. Новые типы будут документироваться после реализации и тестирования.
